## Phase 1: setup

**What:** GitHub repository, VS Code with Git Bash, Python 3.12 on Windows, a project virtual environment
(`.venv`), and the core libraries in `requirements.txt` (pandas, numpy, openpyxl, matplotlib; later scikit-learn and fastembed).

**Why:** a virtual environment keeps this project's libraries separate from everything else on the laptop, so
versions never clash. `requirements.txt` lets anyone rebuild the same environment with one command.

**Problems and fixes**
- First `pip install` failed with a network read error → re-ran with `--default-timeout=100 --retries 10`.
- Pasting into the Git Bash terminal (Ctrl+V) types `^V` → type commands, use the Up arrow, or the VS Code Run button.
- Python code typed into the terminal gives a syntax error → code goes in `.py` files; the terminal only runs them.

## Phase 2: data engineering

| Step | File | Output | Notes |
|---|---|---|---|
| Generate | `src/generate_data.py` | `data/raw/incidents_raw.csv` (3,060 rows) | Seeded (42), deliberately messy: duplicates, blanks, mixed date formats, "p1" vs "Priority 1", resolved-before-opened rows |
| Explore | `src/explore_data.py` | printed profile | shape, column types, missing values |
| Clean | `src/clean_data.py` | `data/processed/incidents_clean.csv` (3,000 rows) | removed 60 duplicates, standardised priorities, parsed both date formats, flagged 28 invalid dates, filled missing group/department, added `resolution_hours` and `sla_met` |
| Load | `sql/schema.sql`, `src/load_database.py` | `data/processed/opspulse.db` | normalised SQLite: `incidents`, `priorities`, `assignment_groups` |

**Design decisions**
- Invalid-date rows are kept but excluded from SLA and resolution time, rather than deleted, so the ticket count stays complete.
- SLA is measured only on resolved tickets with valid dates (2,838). Open tickets have no result yet, so they are neither met nor breached.

**Problem and fix:** the first synthetic data gave unrealistically low SLA (30 to 46%) → retuned typical resolution
times in the generator so normal months sit around 91 to 93%, with deliberate slowdowns in March and August.

## Phase 3: SQL analytics

- `sql/analytics_basic.sql`: GROUP BY and JOINs (volume and SLA by priority, group, category, department).
- `sql/analytics_advanced.sql`: CTEs and window functions: monthly SLA trend with `LAG`, running total, busiest
  technician per group with `RANK`, two slowest tickets per priority with `ROW_NUMBER`, worst category/priority pairs with `HAVING`.
- Run any file with `python src/run_query.py sql/<file>.sql`.

**Found:** SLA dips in March (75.4%) and August (77.1%); P1 is weakest at 77.3%.

## Phase 4: Power BI dashboard

**Steps**
1. `src/export_for_powerbi.py` writes `reports/opspulse_dashboard_data.xlsx`.
2. Power BI model: Incidents, Priorities, a Calendar date table, an Insights helper table and a Refresh Info table; 52 DAX measures.
3. Design went through four versions: 3 pages → a one-page draft built by hand → a dark navy executive page → an audited final version.
4. Saved as `reports/opspulse_executive_dashboard_v2.pbix` and as a Power BI Project
   (`reports/opspulse_executive_dashboard.pbip`), whose model and visuals are text files that Git can track.

**Final page sections:** KPI cards with month-over-month change · monthly volume vs SLA against a 90% target ·
department and group analysis · group scorecard · SLA and resolution by priority · six management insights written
by DAX with On track / Watch / Action status · slicers for month, priority, department and group · Reset filters ·
live filter banner · data period and last-refresh time.

**Problems and fixes**

| Problem | Cause | Fix |
|---|---|---|
| Dates loaded as decimals | Excel stores dates as numbers | Set column data types in Power BI |
| SLA Breaches showed 488, not 326 | In DAX, BLANK = 0 is TRUE, so open tickets counted as breaches | `FILTER(..., sla_met = 0 && NOT(ISBLANK(sla_met)))` |
| Time-intelligence measures errored | A measure can't be used directly inside a CALCULATE filter | Store it in a `VAR` first |
| Colour rules coloured the whole chart | Conditional formatting needed a per-row selector | Added the data-wildcard selector |
| A reviewer said KPIs "did not reconcile" (478 vs 940) | Security Operations was selected: cross-filtering filters other visuals, never the one clicked | Not a data error; added a live "FILTERED VIEW" banner so it is obvious |
| P1 bar looked above the 90% line | Target line used a different axis scale | Locked both axes to 0 to 100% |

**Validation:** every KPI was checked against independent SQL: 3,000 incidents, 134 open, 2,866 closed,
88.5% SLA, 326 breaches, 6.47 hours, plus spot checks under slicers (P1: 141 incidents, 77.3%; Finance: 390, 89.3%;
Security Operations: 478, 50 breaches). Full report in the Power BI guide.

## Phase 6: AI ticket classifier (free)

**Why realistic text was needed:** the original descriptions were labels like "Network issue - VPN", so any model
would score 100% without understanding anything.

| Step | File | Result |
|---|---|---|
| Realistic tickets | `src/generate_ticket_text.py` → `data/processed/tickets_with_text.csv` | 3,000 user-style tickets with typos, urgency hints (10% exaggerated) and misleading words; 368 (12.3%) routed to the wrong team |
| Keyword ML | `src/train_classifier.py` → `models/ticket_classifier.joblib` | TF-IDF + Logistic Regression: 100% on familiar wording but only 60.2% on new wording; priority 70.3% |
| Semantic AI | `src/semantic_classifier.py` → `models/semantic_classifier.joblib` | Free BGE-small embeddings (run locally with fastembed): zero-shot 84.6%, trained 94.9%; catches all 80 misrouted test tickets, 76% of flags correct |

**The honest test:** for each subcategory, one sentence pattern is held out completely, so the test measures
understanding of new wording, not memory. Charts: `reports/ai/ml_confusion_category.png`, `reports/ai/model_comparison.png`.

**Design conclusion:** semantic AI for category and routing, keywords for priority (urgency lives in specific words
like "urgent" or "no rush", where keyword ML scored 70.3% vs 58.6%).

**Cost decision:** the Claude API was considered (about $1 for this module) but the account needed a larger
upfront payment, so the free local model was used instead. A Claude comparison can be added later with an API key in `.env`.

## Phase 8: similar tickets and resolution suggestions

- `src/generate_ticket_text.py` now also writes a realistic `resolution_note` for every resolved ticket (how it was
  fixed). A separate random generator keeps the ticket text identical, so saved AI embeddings stay valid.
- `src/similar_tickets.py` searches resolved tickets by meaning with the same free BGE-small model and suggests the
  team (similarity-weighted vote of the 15 closest), the likely fix (closest match) and the typical time (5 closest).

| Result (623 tickets in unseen wording) | Value |
|---|---|
| Closest past ticket is the same kind of problem (its fix applies) | 76.7% |
| Suggested team is right | 89.2% (original human routing 87.2%) |
| Misrouted tickets it would correct | 67 of 80 |
| When it disagrees with the human routing, it is right | 50.4% |

**Decision:** voting over 5 neighbours gave 86.0%, worse than humans, because past misrouted tickets were copied;
15 neighbours let the right team outvote them. For routing alerts the trained classifier is stronger (76% of its flags
right vs 50%); similar-ticket search adds what a classifier can't: the past fix and real resolution times.

## Phase 9: root cause analysis (problem management)

`src/root_cause_analysis.py` groups all 3,000 tickets by meaning into 28 problem groups with K-Means on the free
embeddings, with no labels. Groups are named by their most distinctive words (greetings, urgency and sign-offs ignored).

| Finding | Detail |
|---|---|
| Grouping quality | 79% of each group is one specific problem, 88% one category (ARI 0.59), checked against known labels |
| Top problem candidates | Password reset (30 breaches, 246 h over SLA), Spam (25, 148 h), Docking station (23, 144 h) |
| Volume spikes | none: no group had a month with significantly more tickets than expected (strict Poisson test) |
| March and August dips | SLA fell in 25 of 28 groups and tickets took about 1.4x longer everywhere, so the cause is systemic (staffing or process), not one technical fault |

The impact score is total impact (hours over SLA 50%, breaches 30%, reopens 20%), so common problems rank high:
that is where a permanent fix saves the most. Outputs: `reports/rca/root_cause_analysis.xlsx`, `problem_impact.png`,
`sla_by_group_month.png`.

## Phase 10: SLA risk prediction (early warning)

All tickets open today are already past SLA, so the useful question is an early warning while a ticket can still be
saved. `src/sla_risk_prediction.py` learns from January to August and replays September and October as unseen future.

| Approach (tested on Sep-Oct) | AUC (0.5 = coin flip) |
|---|---|
| At intake, priority only | 0.56 |
| At intake, ML on every field known when the ticket opens | 0.50 |
| While open, risk table: priority x share of SLA time used | **0.74** |
| While open, ML on every field + share of SLA time used | 0.68 |

- Ticket details do not predict breaches; priority and time already used do. Of tickets still open at 50% of SLA
  time, 29% breached; at 80%, 61%.
- ML scored lower than the simple table because it learned patterns in fields with no real signal, so the
  explainable table is used (`models/sla_risk_table.json`).
- Alert rule: warn when risk reaches 50% (P1 at 60% of SLA time, others at 80%). On September and October: all 55
  breaches warned before they happened, 1.7 alerts per real breach (about 1.5 a day), with 24 minutes (P1) to
  4.8 hours (P4) of warning. Every breach passes the alert point, so the real test is the false-alarm rate.

## Concepts learned (plain English)

| Term | Meaning |
|---|---|
| Virtual environment | a private set of Python libraries for one project |
| Normalisation | storing each fact once (e.g. SLA targets in their own table) and linking with keys |
| CTE | a named temporary result inside one SQL query (`WITH ... AS`) |
| Window function | a calculation across related rows without collapsing them (`LAG`, `RANK`, `AVG() OVER`) |
| DAX measure | a calculation in Power BI that responds to filters |
| Cross-filtering | clicking one visual filters the others, but not itself |
| PBIP | Power BI saved as text files, so Git can track changes |
| Train/test split | learn from some data, measure on data the model has never seen |
| Memorisation (overfitting) | scoring well on familiar examples but failing on new ones |
| TF-IDF | turns text into numbers based on which words are distinctive |
| Embedding | numbers that capture the meaning of a sentence |
| Zero-shot | classifying without any labelled examples, only descriptions |
| Nearest neighbours | answering from the most similar past examples |
| Clustering (K-Means) | grouping items that are alike without being told the groups |
| AUC | how well a score ranks positives above negatives: 0.5 is a coin flip, 1.0 is perfect |
| Time-based split | train on earlier months, test on later ones, as in real use |
| Problem vs incident (ITIL) | an incident is one interruption; a problem is the underlying cause behind repeated incidents |
| Precision / recall | of the items flagged, how many were right / of the real items, how many were caught |

## Interview talking points

1. **End to end:** "I built a pipeline from raw messy ITSM data to a cleaned SQLite database, SQL analytics, a
   validated Power BI executive dashboard, an automated monthly report and an AI ticket classifier."
2. **Data quality:** "I kept invalid-date tickets but excluded them from SLA, so counts stay complete and SLA stays honest."
3. **Validation:** "Every dashboard number was cross-checked against independent SQL."
4. **The 478 question:** "A reviewer thought the KPIs didn't reconcile. It was cross-filtering, not bad data,
   so I added a live filter banner to make the context obvious."
5. **AI judgement:** "Keyword ML scored 100% on familiar wording and 60% on new wording. A free semantic model reached
   95%. For priority, keywords were better, so the right design is hybrid."
6. **Automation:** "A report that takes an analyst hours each month now takes one command."
7. **Root cause:** "Grouping tickets by meaning showed the March and August SLA dips hit 25 of 28 problem types at
   once, which points to a staffing or process cause rather than a single broken system."
8. **Simple beats complex:** "For SLA breach prediction, a risk table of priority by time used scored AUC 0.74 on
   unseen months and beat machine learning (0.68), so I shipped the explainable rule."
9. **Workforce:** "I found Service Desk technicians carry nearly twice the load of Desktop Support, and compared
   technicians fairly by normalising resolution time against each ticket's SLA target."
